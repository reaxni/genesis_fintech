# Genesis G0 — общий контракт v1.0

Внешние требования заданы кейсом и опубликованными определениями проверок. Здесь зафиксированы решения команды для связывания частей A, B и C. G0 считается опубликованным после review и входа в основную ветку.

## Точки интеграции

- A экспортирует `genesis_audit.data.generate_episode(seed, config, output_dir)`. Внешний адаптер вызывает его с непреобразованным config. Настройки генератора и допустимые значения A документирует в отдельном модуле. Они включают независимое включение четырёх ошибок и два сочетания.
- B экспортирует `genesis_audit.env.AuditEnv(*, generate_episode, score_episode)`. Оба аргумента — callbacks, совместимые с judge adapter. Сам `reset(seed, config)` в closed использует переданный `episode_dir` как есть. В train без каталога вызывается генератор через callback с `team_config`. Для локального runner B также предоставляет `truncate()`, который завершает тайм-аут как truncated с пустым итогом. Эта операция недоступна политике.
- C экспортирует `judge_adapter.generate_episode(seed, config, output_dir)`, `make_env()` и `score_episode(episode_dir, findings, inspection_steps)`. Три команды ролей расходятся только в своих модулях. Контракты типов в `genesis_audit.contracts.v1`. C принимает изменения общего формата отдельным PR.
- B экспортирует `genesis_audit.policies.choose_action(policy_name, observation, history, *, rng)`. Имена `random`, `reconciliation` и `mark_all`. `history` содержит предыдущие публичные пары `{"observation": ..., "action": ...}` текущего эпизода. `rng` принадлежит политике, сбрасывается с фиксированным числом 0 для демонстрационного прогона и не связан с seed генератора. Возврат — одно публичное действие в формате step.
- `step` принимает `{"name": "...", "args": {...}}`; у submit аргумент `findings` целиком, включая episode_id. Ответы reset/step, обязательные ключи, пять действий, 50/100/60 и правила штрафов — из спецификации. Ошибки содержат публичные коды. В closed агент видит числовой ноль даже на submit; в train допускается итоговый return, без приватных деталей.

## Граничные случаи API

- Структурно неверный `submit` завершает эпизод с `terminated=true` и ошибкой `invalid_submit`. Оценщик ставит −1. В closed публичная награда по-прежнему равна 0. Последующие действия возвращают `episode_finished`.
- `list_records` принимает целый положительный `limit`. Значение выше 50 сокращается до 50. Ноль, отрицательное значение, логический тип и дробное число дают `invalid_args`.
- Курсор первой страницы — `null`. `next_cursor` имеет вид `<table>:<offset>`, где offset — десятичная позиция в таблице. Политика передаёт полученный курсор как непрозрачную строку. Для одной таблицы, курсора и размера страницы записи и порядок стабильны в пределах эпизода. Чужая таблица, неверный формат или позиция за пределами таблицы дают `invalid_cursor`.
- Публичные коды ошибок — `unknown_action`, `invalid_action`, `invalid_args`, `unknown_table`, `unknown_id`, `unknown_document`, `invalid_cursor`, `calc_*`, `invalid_submit`, `episode_finished`, `timeout`. Некорректное исследовательское действие расходует один шаг.

## Данные и пути

`manifest.json` — schema_version "1.0", episode_id, base_currency, period_start, period_end, timezone, row_count, document_count, rounding, currency_exponents. `policy.json` — публичные правила `period_boundary`, `fx_date_basis`, `rounding` и необязательный `amount_tolerance_minor` (карта тип → фиксированный целый допуск, по умолчанию 0). В v1 обычная политика использует интервал [start,end), округление HALF_EVEN и дату хозяйственного события в локальной зоне эпизода. Время ISO-8601 со смещением, деньги целые, FX десятичной строкой. У разных валют различная разрядность. При работе с документами сохраняется порядок записей.

Публичные поля из §03 кейса сохраняются. Дополнительные поля v1, если нужны сценарию:

| Файл | Поле | Назначение |
|---|---|---|
| ledger.csv | posting_group_id, event_at | Связь двойной записи и дата хозяйственного события для проверки даты признания |
| ledger.csv | allocation_minor, allocation_currency | Фактическое распределение в валюте платежа. Заполнять на одной строке распределения, остальные null |
| ledger.csv | fx_source_minor, fx_source_currency | Исходная сумма операции на одной валютной проводке. Прочитанная сумма в базовой валюте берётся из её дебета или кредита |
| payments.jsonl | intended_allocations | Список объектов invoice_id, amount_minor, currency из назначения платежа |
| invoices.jsonl | source_reference | Исходная бизнес-ссылка, если используется для сверки |

CSV пустая ячейка nullable поля означает JSON null в наблюдении. Для JSON-ссылок используется null, списки ссылок сохраняют порядок. Глобально уникальные evidence ID — row_id для ledger, doc_id для документов и `date:source_currency:target_currency` для FX. Для `get_record` в invoices/payments используются invoice_id/payment_id, для `get_document` — doc_id. Для FX `get_record` принимает бизнес-ключ. Не кодировать тип ошибки или seed в публичных ID.

`truth.json` — объект `{"issues": [...]}` по схеме. У каждой ошибки один канонический набор `affected_ids` и один или несколько допустимых полных массивов `evidence_sets`. `provenance.json` — `{"schema_version":"1.0", "changes":[...]}`. Доверенная запись мутации описывает сущности, правило, до/после и порядок. Вместе с документами этого хватает для независимой проверки. Оба файла недоступны процессу политики. Наличие ID в приватных файлах не добавляет его к доступным доказательствам.

| Тип | Канонические affected_ids | Сумма и доказательства |
|---|---|---|
| duplicate_invoice | invoice_id и row_id повторной группы | Повторно отражённая сумма обязательства в валюте отражения. Счёт и обе группы позволяют распознать дублирование. Повтор может отражать итог на нескольких строках одного счёта учёта |
| payment_allocation | payment_id и invoice_id | Недостача распределения в валюте платежа. Назначение, счёт и запись распределения или имеющиеся публичные записи, доказывающие его отсутствие |
| fx_conversion | row_id валютной строки | Абсолютная разница ожидаемой и фактической суммы в базовой валюте. Дата, курс и исходная сумма доступны |
| period_cutoff | row_id строк неверно признанной группы | Сумма группы в валюте отражения, одна сторона двойной записи. Сравнить дату события и дату признания с границами периода |

Набор affected_ids не изменяется добавлением посторонних строк. Суммы описывают отдельные расхождения, поэтому суммы взаимодействующих ошибок могут пересекаться. Matcher не объединяет их.

## Проверяемые примеры

- Ручная фикстура `tests/integration/fixtures/g0_partial_payment` показывает счёт 120 000 ₸, два поступления 50 000 ₸ и 70 000 ₸, из второго распределлено 20 000 ₸. Должно быть 70 000 ₸. Итог 50 000 ₸, в minor units 5 000 000. `expected_findings.json` и метрики — файлы теста, никогда не содержимое наблюдения. Для чистого варианта вторую сумму полностью распределить и оставить пустой truth.
- Дубль: обязательство 10 000 ₸ отражено второй группой на 10 000 ₸. Одни и те же суммы на разных счетах не являются дублем.
- FX: 100 USD при 500 KZT/USD должны дать 50 000 KZT; запись 49 000 KZT даёт отклонение 1 000 KZT.
- Cutoff: событие 1 марта, признано 28 февраля в зоне эпизода, хотя правило относит его к марту. Сумма группы известна по проводкам.
- Взаимодействие 1: из 100 USD распределили 80 USD. Это ошибка 20 USD. На отражённых 80 USD применили 490 вместо 500 KZT/USD. FX-ошибка 800 KZT. Первую доказывают назначение и распределение, вторую — исходная отражённая сумма, курс и базовая проводка.
- Взаимодействие 2: одна группа отражения счёта на 120 000 KZT находится вне требуемого периода, а вторая отражает то же обязательство повторно. Источник и обе группы доступны публично. Cutoff указывает строки первой группы, дубль — invoice_id и строки второй группы. Обе оценки 120 000 KZT относятся к разным фактам; их не складывают в «ущерб».
