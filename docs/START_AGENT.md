# Стартовое поручение координатору
## Старт трёх независимых сессий

Один человек с доступом к GitHub создаёт общий репозиторий команды и загружает стартовый пакет. Каждый участник клонирует репозиторий **в свой каталог** и запускает свою модель в этом клоне. Назначьте каждому человеку ровно одну роль A/B/C. Для этого режима скопируй соответствующий текст ниже. Стартовое поручение координатору для одной сессии сохранено дальше.

Общий текст для всех трёх моделей:

> Работаешь в отдельном клоне Genesis. Прочти AGENTS.md, docs/ARCHITECTURE.md, docs/WORK_PLAN.md и docs/TASKS.md. Проверь origin и состояние через git status, git remote -v и git rev-parse HEAD. Открой рабочую ветку от актуального origin/main, либо продолжи уже созданную ветку своей роли. Меняй только пути своей роли. Используй GitHub PR как журнал работы и связи с другими ролями. Сохраняй прогресс небольшими коммитами и отправляй только свою ветку. В PR укажи базу, версию схемы, результаты проверки и зависимые PR. Если нужен чужой файл, предложи точную правку с примером в PR или issue, затем продолжай независимую часть. Перед окончательной отправкой обновись от origin/main по docs/WORK_PLAN.md и повтори свои проверки. Не отправляй секреты и приватные результаты закрытых эпизодов.

| Роль | Текст, который добавляется к общему |
|---|---|
| **A. Data + Verification** | «Работай в ветке work/data-t02. Отвечай за T02, T05, T06 и часть T07 с открытыми эпизодами. Начни с проверки экспорта ручной фикстуры G0, затем добавь чистую историю, мутации и независимый верификатор. Для T06 подготовь преобразования заранее, сквозные пары прогони после интеграции. Общие схемы оставь роли C.» |
| **B. Environment + Policies** | «Работай в ветке work/env-t03. Отвечай за T03 и три обычные политики T07. Начни с reset/list/get/submit на фикстуре G0 и отдельного теста состояния, затем добавь границы бюджета, транспорт и изоляцию. Используй согласованный callback или заглушку в unit-тесте, пока scorer не объединён. Compose и общий запуск согласуй с C.» |
| **C. Scoring + Integration** | «Сначала открой work/bootstrap-t00. Закрепи контракт, общую фикстуру и команды проверки, опубликуй SHA после merge. Затем в work/scoring-t04 реализуй T04, общую сборку, oracle и интеграцию. Веди общие схемы и миграции отдельными PR. Принимай изменения A/B последовательно после проверки и собирай G1/G4. Для своего PR получи проверку A или B.» |

Пример для роли A после появления `origin/main`:

```bash
git clone <URL_репозитория> genesis-data
cd genesis-data
git fetch origin
git switch -c work/data-t02 origin/main
git status --short
# После изменений и тестов добавь только свои файлы.
git add -- <точные_пути_изменённых_файлов>
git commit -m "T02: add episode generation"
git push -u origin work/data-t02
```

Значения в угловых скобках замени своими перед запуском. Роли B и C используют свои ветки и каталоги. После push открой PR в `main` по шаблону репозитория. Пока G0 не принят, PR A/B могут оставаться черновиками. Роль C сообщает о готовности планом и ссылкой на коммит в GitHub.

## Старт одной сессии
Скопируй текст ниже в новую сессию Codex, открытую в папке Genesis.

> Реализуй Genesis FinTech по AGENTS.md, docs/WORK_PLAN.md, docs/ARCHITECTURE.md, docs/TASKS.md и полным исходным определениям в docs/sources.
> Начни с T00 и G0: зафиксируй схемы, бухгалтерскую модель, error types, config, публичные ID и API judge_adapter. Затем сделай вертикальный срез T01.
> Используй Python 3.11, файловые эпизоды и контракты из CONTRACT_G0.md. Scorer роли C использует стандартную библиотеку, максимальное паросочетание и отдельный tie-break. Пиши тесты unittest и фиксируй seed. Быстрая проверка: bash scripts/check.sh. Полная проверка после интеграции A/B: bash scripts/verify.sh в Linux.
> В рамках T00 проверь кандидат R3n0va как временный источник чистой истории. Зафиксируй commit, отключи DQ, сравни два запуска на одном seed, затем проверь, сохраняются ли сумма, валюта, дата, распределение и все ссылки в срезе одной компании за период. Сохрани лог принятия решения. Отведи до 90 минут. При неясных связях или неприменимости используй собственный генератор событий. Публичный экспорт должен быть одинаковым для обоих путей.
> До параллельной работы вручную проверь чистый split-payment, четыре одиночные ошибки и оба сочетания. Для каждого используй пример с цифрами, canonical affected_ids, полный evidence set и правила округления. Отдельно докажи, что две мутации не уничтожают доказательства друг друга.
> Сначала собери сдаваемую RL-среду. Обязательны reset/step, записанные траектории и проверка качества. Демо запусти скриптовой сверкой. Подготовь также адаптеры random, mark-all и oracle. Oracle использует эталон только в доверенном процессе и подаёт обычный submit. Адаптер жюри переводит формат и не выбирает действия вместо внешней политики.
> Прогони C01–C20, D01–D20, локальные R01–R20 и M01–M12, затем P01–P20. Для проверки данных используй независимый пересчёт. Для пар загружай исходные и преобразованные файлы через episode_dir. Проверяй closed reward=0 и доступ к закрытым файлам на уровне ОС. README должен указывать рабочую директорию внутри контейнера, три точки входа, документированные типы и одну команду проверки.
> Обучение весов опционально. Если команда решит проводить эксперимент после готовности комплекта, используй раздел «Что понадобится, если команда решит обучать веса» в ARCHITECTURE.md. Зафиксируй baseline и held-out, обучай на дополнительных train-эпизодах и сравни по качеству и расходу действий. Запуск сдачи и демо должны работать без весов, GPU и платных API.
> После фиксации интерфейсов делегируй независимые части агентам по ролям data_engineer, env_engineer, reward_engineer. Их инструкции находятся в agent-config/agents/*.toml; если custom roles не установлены, передавай эти инструкции обычным subagents. Используй verifier_engineer для независимых проверок после G0, reviewer для проверки стабильного среза.
> Выполняй задачи по зависимостям до готового проверяемого пакета; общие контракты интегрируй сам. Не жди подтверждения на обычные обратимые действия внутри проекта. Не публикуй и не отправляй материалы организаторам без отдельного поручения.
> Покажи реальные команды и результаты. Не обещай баллы и не называй локальную матрицу скрытыми проверками жюри. Если Docker недоступен, проверь доступные части и честно обозначь блокировку проверки контейнера/изоляции.
> Заверши одной командой проверки, 10 train + 10 dev эпизодами, четырьмя адаптерами политик, trajectories.jsonl, design note и демо. Уникальные дополнения делай после обязательного ядра без изменения общей reward.
