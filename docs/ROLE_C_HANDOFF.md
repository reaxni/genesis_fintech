# Проверка сборки Genesis

Генератор, среда и оценщик объединены в `main` на коммите `d2aaec3`. Полная проверка запускается на Ubuntu командой `bash scripts/verify.sh`. GitHub Actions сохраняет три журнала как артефакт `genesis-verification`.

## Полный прогон

На `main` с коммитом `d2aaec3` команда `bash scripts/verify.sh` прошла на Ubuntu с Python 3.11.11 в Docker. Все 102 теста полного задания прошли, контейнер проверки завершился с кодом 0. Архив JSONL весит 950 470 байт. [Запуск main](https://github.com/reaxni/genesis_fintech/actions/runs/44896650285)

| Политика | Эпизоды | TP | FP | FN | Средний return |
|---|---:|---:|---:|---:|---:|
| Oracle | 20 | 20 | 0 | 0 | 1.000 |
| Сверка | 20 | 20 | 0 | 0 | 0.980 |
| Случайная | 20 | 0 | 40 | 20 | −1.000 |
| Отметить всё | 20 | 0 | 600 | 20 | −1.000 |

В T08 прошли те же 102 теста. Демо завершилось за 11 действий, итоговая награда составила 0.980. Архив из трёх журналов весит 953 276 байт. [Первый прогон T08](https://github.com/reaxni/genesis_fintech/actions/runs/44896987260)

## Диагностика

- Matcher проверен по R01–R20, M01–M12 и полным перебором 512 малых графов. Роль A отдельно сверила штраф, дубликат ответа, недоступное доказательство и два случая неоднозначного сопоставления. [Ревью оценщика](https://github.com/reaxni/genesis_fintech/pull/2)
- Разные имена проекта при сборке и запуске Compose мешали использовать собранные образы. Теперь один вызов скрипта собирает и запускает образы под одинаковым именем проекта. [История проверки](RETROSPECTIVE.md)
- Роль B измерила прерывание зависшей политики через 60.03 с и медленной через 60.01 с на Linux arm64. В обоих случаях итоговый список находок пуст. Команда для повтора — `bash sandbox/run_isolation_checks.sh`. [Отчёт роли B](../sandbox/README.md)

На открытых эпизодах случайная политика дала 40 ложных находок и пропустила все ошибки. Политика «отметить всё» дала 600 ложных находок. Сверка платежей, проводок и дат дала 20 верных находок на том же корпусе. Отдельные строки результатов доступны в `metrics.jsonl`.

## Границы оценки

Результаты относятся к открытому корпусу. Oracle получает эталон и проверяет цепочку scoring. Скриптовая сверка работает по наблюдениям среды. Финальный балл определит жюри на закрытых эпизодах. Лимит времени среды составляет 60 секунд, фактическое завершение внешнего процесса зависит от планировщика Linux.
